# Architecture

## Overview

This system is an outbound voice-call harness that places real phone calls to the PGAI test line, simulates a patient conversation using an LLM-backed reply engine, and records the full conversation for analysis. It is optimized for reliability and signal quality: every design decision trades engineering complexity for call fidelity and clean evidence collection.

The call path can be triggered one scenario at a time from the dashboard UI, run as a full batch from the CLI, or fired directly via the REST API.

## Key components

### Reply engine (`engine.py`)

The patient reply is generated by GPT-4o-mini via an OpenAI-compatible API call. The engine receives the full conversation transcript, the scenario objective, the patient profile, and call memory (confirmed facts, recent questions), and returns a 1-2 sentence response appropriate for a real patient in that situation.

This is intentionally not a scripted response tree. PGAI's agent takes unexpected paths — demanding addresses, asking about things out of order, looping on the same question. A scripted bot would fall off the track immediately. The LLM engine adapts turn by turn, which is what produces meaningful bug evidence.

The engine has a deterministic rule-based fallback for when the LLM is unavailable or quota-limited.

Three guards run before the LLM is called on every turn:
- **CONFIRMATION_RE** — catches mid-call confirmation questions ("is that correct?") and returns an affirmative without hanging up
- **GOODBYE_RE** — catches genuine closing phrases and triggers a clean hangup
- **Repetition detection** — if PGAI asks the same question twice, the bot flags it rather than looping

### Disclaimer buffer (`app.py: maybe_stage_office_speech`)

PGAI opens every call with a recorded disclaimer ("This call may be recorded...") before the live agent speaks. Twilio's `<Gather>` sometimes delivers this as two rapid STT results rather than one complete turn — the disclaimer fires as a fragment, and the gather fires again before PGAI finishes speaking.

Without handling this, the bot would reply to a cut-off disclaimer fragment before the agent has asked anything. The buffer holds the first fragment if it looks like a disclaimer opener and merges it with the next result before passing it to the reply engine.

### Call memory (`app.py: CallMemory`)

Each call session maintains a structured memory object that tracks:
- Scenario objective and required/optional facts
- Patient profile (name, DOB, medication, pharmacy, etc.)
- Recent office questions and patient answers (last 5 each)
- Confirmed facts — automatically extracted when the patient's reply contains profile values
- Current phase (opening / office_turn / patient_turn)

This memory is passed to the LLM on every turn so the patient's replies stay coherent across the full conversation, not just the last exchange.

### SSE event hub (`app.py: CallEventHub`)

Every significant event during a call is published to a per-call SSE stream at `/events/{call_sid}`. The dashboard subscribes to this stream and renders each event in real time.

Event types:
| Event | When |
|---|---|
| `session_started` | Call session created |
| `transcript_line` | Each office or patient turn |
| `call_status` | Raw Twilio status callback |
| `call_completed` | Call fully ended (any reason) |
| `recording_ready` | MP3 downloaded and saved |

The hub keeps a 200-event history per call so the dashboard can replay the full call when loading a past session.

### Voice (`TWILIO_VOICE`)

Patient speech uses **Google Chirp3 HD (Aoede)**, configured via `TWILIO_VOICE=Google.en-US-Chirp3-HD-Aoede`. This was chosen after testing Polly.Matthew-Neural, which sounded robotic over the phone codec. Chirp3 HD produces natural-sounding conversational speech that holds up through Twilio's telephony layer.

## Why this design

**Twilio-native STT/TTS instead of a custom media stream.**
A raw media stream would require handling audio codecs, streaming buffers, and a custom ASR pipeline. Twilio's `<Gather>` handles all of this and returns clean text. The tradeoff is slightly higher latency per turn, but call quality and reliability are far better for the amount of engineering involved.

**LLM-backed replies instead of a script.**
Scripted bots break the moment PGAI does something unexpected. The LLM engine costs ~$0.001 per turn and handles PGAI's deflections, loops, and policy gates without manual case handling for every possible response.

**Session state in memory, artifacts on disk.**
Active call state is kept in a Python dict (fast, no DB dependency). After every turn the session is written atomically to disk as JSON and readable text. This means a process crash loses at most one turn and the transcript is always consistent.

**Pluggable reply engine.**
The `ReplyEngine` base class is implemented by both `OpenAICompatibleReplyEngine` and `RuleBasedReplyEngine`. If the LLM quota is exceeded mid-session, the app falls back to the rule-based engine automatically without dropping the call.

**Single allowed destination.**
`ALLOWED_TARGET_NUMBER` is validated on every outbound call attempt. The code refuses any other destination in `sanitized_target_number()`. This prevents accidental calls to real patients regardless of what is passed to the API.

## Tradeoffs and what was deliberately left out

- **No streaming audio** — Twilio's `<Gather>` introduces ~1-2 seconds of latency between PGAI's speech ending and the bot's reply starting. This is acceptable for testing; a production real-time agent would need a streaming stack.
- **No database** — transcript files on disk are the canonical store. This is sufficient for a single-machine test harness and keeps the setup to a single `pip install`.
- **No authentication on the dashboard** — it runs on localhost only. The public-facing endpoints are Twilio webhooks, which are protected by signature validation.
- **GPT-4o-mini not GPT-4o** — the patient replies are short (1-2 sentences) and the scenarios are well-defined. GPT-4o-mini handles this correctly and is significantly cheaper. GPT-4o would not meaningfully improve call quality for this use case.
