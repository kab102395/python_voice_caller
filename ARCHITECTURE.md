# Architecture

The bot uses Twilio to place outbound calls to the PGAI test line. When the call connects, Twilio hits a FastAPI webhook (`/twiml`) that creates a session and returns a `<Gather>` verb to listen for speech. Each time PGAI speaks, Twilio transcribes it and posts the text to `/voice`. The server runs it through a GPT-4o-mini reply engine that generates the next patient response based on the scenario objective, patient profile, and a running call memory of confirmed facts. That reply gets spoken back via `<Say>`, and the loop repeats until the call ends naturally or hits a turn/time limit. Recordings are downloaded from Twilio after each call and stored alongside JSON and plain-text transcripts in `artifacts/`.

The main design choices were driven by wanting real signal fast. Using Twilio's built-in STT/TTS instead of a custom audio pipeline meant the first real call happened in hours, not days. Using GPT-4o-mini for patient replies instead of a scripted response tree meant the bot could handle whatever PGAI said — deflections, policy gates, mid-call pivots — without manually coding every branch. A live dashboard streams each turn over SSE so you can watch calls as they happen and catch issues in real time. The only hard constraints are a destination allowlist (only `+18054398008` can be called) and Twilio webhook signature validation on every inbound request.
