# Pretty Good AI — Voice Testing Bot

An automated voice agent that calls the PGAI test line, simulates realistic patient scenarios, records both sides of every conversation, and documents bugs in the PGAI agent's behavior.

Built for the [Pretty Good AI Engineering Challenge](https://pgai.us).

---

## What this does

The bot places real outbound phone calls using Twilio, acts as a patient interacting with the PGAI voice agent, and records the full conversation. After each call it writes a structured JSON transcript, a human-readable `.txt` transcript, and an MP3 recording. A live dashboard streams every turn in real time as the call happens.

The patient voice is powered by Google Chirp3 HD (via Twilio) for natural-sounding speech. Patient replies are generated by GPT-4o-mini, which adapts to whatever PGAI says rather than following a rigid script. This lets the bot handle unexpected PGAI turns, recover from dead ends, and steer toward the intended test objective — just like a real patient would.

## Architecture

```
launcher.py
    ├── starts uvicorn (app.py) on port 8000
    ├── starts ngrok, reads tunnel URL, patches BASE_URL in .env
    └── opens dashboard in browser

app.py  (FastAPI)
    ├── POST /twiml          ← Twilio calls this when the call connects
    ├── POST /voice          ← Twilio posts STT results here each turn
    ├── POST /status         ← Twilio call status callbacks
    ├── POST /recording-status  ← Twilio recording ready callbacks
    ├── GET  /events/{sid}   ← SSE stream of live call events per call
    ├── GET  /dashboard      ← serves the operator dashboard
    ├── POST /api/call       ← trigger a call from the dashboard
    ├── GET  /api/calls      ← call history from transcript files
    ├── GET  /api/scenarios  ← scenario catalog
    └── GET  /api/bugs       ← bug report index

engine.py
    ├── OpenAICompatibleReplyEngine  ← GPT-4o-mini backed patient replies
    └── RuleBasedReplyEngine         ← deterministic fallback

scenarios.py    ← 10 test scenarios with objectives, starters, followups
clients.py      ← Twilio REST + TwiML helpers
config.py       ← env validation
call_service.py ← outbound call trigger
```

## Quick start

**Requirements:** Python 3.11+, a Twilio account, an ngrok account, an OpenAI API key.

### 1. Install dependencies

```powershell
pip install -r requirements.txt
```

### 2. Configure environment

```powershell
Copy-Item .env.example .env
```

Open `.env` and fill in your credentials. The required fields are:

| Variable | Description |
|---|---|
| `TWILIO_ACCOUNT_SID` | Twilio account SID |
| `TWILIO_AUTH_TOKEN` | Twilio auth token |
| `TWILIO_PHONE_NUMBER` | Your Twilio number (E.164 format) |
| `NGROK_AUTHTOKEN` | ngrok auth token |
| `LLM_API_KEY` | OpenAI API key |
| `BASE_URL` | Set automatically by launcher — leave blank |

Optional:

| Variable | Default | Description |
|---|---|---|
| `LLM_MODEL` | `gpt-4o-mini` | OpenAI model for patient replies |
| `TWILIO_VOICE` | `Google.en-US-Chirp3-HD-Aoede` | TTS voice |
| `MAX_CALL_TURNS` | `30` | Hard turn limit per call |
| `MAX_CALL_SECONDS` | `240` | Hard time limit per call |
| `ALLOWED_TARGET_NUMBER` | `+18054398008` | Safety allowlist — do not change |

### 3. Launch

```powershell
python launcher.py
```

This starts the app, creates a public ngrok tunnel, patches `BASE_URL` automatically, and opens the dashboard. No manual ngrok setup needed.

## Running calls

### From the dashboard

Open `http://localhost:8000/dashboard`. Select a scenario from the dropdown and click **Start Call**. The live transcript streams turn by turn as the call happens.

### From the command line

Single call:
```powershell
python call_runner.py --scenario scheduling
```

Full batch (all 10 scenarios):
```powershell
python batch_runner.py
```

Dry run (no real call placed):
```powershell
python call_runner.py --scenario scheduling --dry-run
```

## The 10 test scenarios

Each scenario is designed to expose a specific failure mode in the PGAI agent. They are not happy-path demos — they are stress tests.

| Scenario | What it tests |
|---|---|
| `scheduling` | Basic booking — does the agent collect required details without drifting? |
| `reschedule` | Existing appointment move — does the agent preserve context across slot selection? |
| `cancel` | Clean cancellation — does the agent confirm and close without unnecessary turns? |
| `refill` | Routine medication refill — does the agent ask for the right details? |
| `controlled_refill` | Adderall refill — does the agent recognize controlled substance policy? |
| `identity_wrong_dob_persistent` | Caller gives wrong DOB and persists — does the identity gate hold? |
| `scheduling_impossible_constraint` | Every slot rejected — does the agent de-escalate or loop forever? |
| `scheduling_pivot_mid_flow` | Mid-call intent switch — does the agent handle a conversation pivot? |
| `insurance` | Coverage question — does the agent answer conservatively without hallucinating? |
| `escalation_demands_human` | Caller demands a human — does the agent hand off instead of deflecting? |

Full scenario rationale: [docs/hard-edge-case-scenarios.md](docs/hard-edge-case-scenarios.md)

## Artifacts

Every call produces three files under `artifacts/`:

```
artifacts/
├── transcripts/
│   ├── <timestamp>_<scenario>_<sid>.json   ← structured call record
│   └── <timestamp>_<scenario>_<sid>.txt    ← human-readable transcript
└── recordings/
    └── <timestamp>_<scenario>_<sid>_<rid>.mp3
```

Historical runs across all sessions are preserved in `artifacts/history/` as an iteration log. Each subdirectory is a snapshot of a complete testing session with its own logs, transcripts, recordings, and bug reports from that point in time.

## How it iterates

The patient reply engine adapts to PGAI's actual responses using GPT-4o-mini. When PGAI takes an unexpected path, the engine generates a contextually appropriate reply based on the scenario objective and call memory — rather than falling off a scripted track. This is what allows the bot to navigate PGAI's deflections, loops, and policy gates and still produce meaningful call evidence.

Key behaviors tuned through iteration:
- **Disclaimer buffering** — PGAI opens every call with a recorded disclaimer that Twilio sometimes splits across two STT results. The bot holds the first fragment and merges it before replying.
- **Identity front-loading** — every scenario opener includes full name and DOB so PGAI's identity gate is satisfied on turn one, avoiding a 14-second dead-air timeout.
- **Confirmation guard** — mid-call confirmation questions ("is that correct?") are answered affirmatively rather than triggering a goodbye.
- **Repetition detection** — if PGAI asks the same question twice, the bot flags it instead of looping.

## Safety

- The call runner only allows calls to `+18054398008`. Any other destination is rejected in code.
- Twilio webhook signatures are validated on every inbound request.
- `.env` is gitignored. `.env.example` contains only placeholder values.
- Recording downloads use Twilio account credentials, not unauthenticated fetches.
- Session transcripts are written atomically to avoid partial files on process interruption.
